title: Installation
description: Install OpenBoxGL 3.0 on Linux with AppImage, Flatpak, or source, on Windows with the signed portable installer, or on macOS with the signed universal app bundle.
---

OpenBoxGL 3.0 runs on Linux, natively on Windows since 1.13.0, and natively on macOS since 1.19.0. Every packaged build ships the native Rust server `openbox-server` with **no bundled Python runtime**. On Linux the AppImage is the recommended path. On Windows the signed portable installer is the supported path; it is covered in full on the [Windows](/windows/) page. On macOS the signed universal app bundle installs with `install-macos.sh`, and the [macOS](/macos/) page covers it in full.

There is no OpenBox account, installer wizard, or license key. Downloading a release or cloning the repository is the entire installation.

## Decide which package to use

| Package | Best for | Updates |
| --- | --- | --- |
| [AppImage](#appimage) | Desktop, Steam Deck, handhelds, immutable systems | Built-in verified updater |
| [Flatpak](#flatpak) | Sandboxed installs from a bundle or manifest | Your normal Flatpak workflow |
| [Source](#source--system) | Development, testing, or patching | `git pull` and rebuild |
| [System install](#source--system) | Installing to `/usr/local` from source | `sudo make install` again |
| [Windows portable](#windows) | Windows 10 and 11, x86_64 or ARM64 | Re-run `install.ps1` from the new release |
| [macOS](#macos) | macOS 11 or newer, Apple Silicon or Intel | Re-run `install-macos.sh --replace` from the new release |

The fastest path on Linux is the [versioned release installer](#versioned-release-installer): download the tag-pinned script, inspect it, then run it. It selects the matching AppImage, pins the release public key, verifies its SHA-256 checksum and Ed25519 signature, and installs it to `~/.local/bin`.

On Windows, download the release's Windows archive for your architecture (`OpenBox-x86_64-windows.zip` or `OpenBox-arm64-windows.zip`), extract it, and run the bundled installer at `OpenBox\scripts\install.ps1`: it verifies the same key pin, checksum, and signature before extracting the portable install to `%LOCALAPPDATA%\OpenBox`, registering the Start Menu shortcut and the `openbox://` handler, and adding the launchers to your user `PATH`. The full walkthrough is on the [Windows](/windows/) page.

<Callout type="note" title="The in-app install step is AppImage-only in 3.0">
The built-in updater checks for updates on every platform, but the verified install step in the 3.0 Rust server is implemented for the AppImage only. On Windows and macOS, install a new release by running the new release's `install.ps1` or `install-macos.sh --replace`. See [Updating](/updating/) for the current behavior.
</Callout>

<Callout type="tip" title="No Python runtime to install">
The packaged application is the Rust `openbox-server` binary plus the native window host. You do not need Python to run it. Python 3.11+ is used only for the optional `OPENBOX_BACKEND=python` fallback, `.py` plugin entrypoints, and the signed installer scripts that verify a release.
</Callout>

<InstallOptionCard slot="appimage">

 ### AppImage

 The AppImage is a single executable file that bundles OpenBoxGL 3.0, the native host, and the Rust `openbox-server`. It does not need to be "installed" system-wide and works on immutable images like SteamOS and Bazzite. The 3.0 builds are 9.7 MiB (x86_64) and 9.0 MiB (aarch64).

 #### Versioned release installer

 Download the installer from a specific signed release, inspect it, then run it. The installer verifies the release public-key pin, SHA-256 checksum, and Ed25519 signature before installing to `~/.local/bin`:

 ```bash
 VERSION=3.0.0
 curl --proto '=https' --tlsv1.2 --fail --location \
   --output install.sh \
   "https://github.com/vindeckyy/OpenBoxGL/releases/download/v${VERSION}/install.sh"
 less install.sh
 OPENBOX_RELEASE_TAG="v${VERSION}" bash install.sh
 ```

 `VERSION` is the current release, **3.0.0**. Pin it deliberately only when reproducing a specific build, because security fixes are not backported to older releases (see [Security](/policies/security/)). The `install.sh` file is itself fetched from that tag, so the download needs a tag either way; dropping the `OPENBOX_RELEASE_TAG="v${VERSION}"` prefix lets the installer resolve the latest release at run time instead.

 The installer needs `curl`, `python3` 3.11+, `openssl`, and `sha256sum` on `PATH`: it verifies the release public-key pin, the SHA-256 checksum, and the Ed25519 signature before installing to `~/.local/bin`.

 To launch OpenBox right after installing, pass `--run` after the tag-pinned invocation:

 ```bash
 OPENBOX_RELEASE_TAG="v${VERSION}" bash install.sh --run
 ```

 Omit `OPENBOX_RELEASE_TAG` only when you intentionally want the latest stable release. Install to a different directory with `OPENBOX_INSTALL_DIR` (e.g. `OPENBOX_INSTALL_DIR="$HOME/Applications"`).

 The installer detects `x86_64` or `aarch64` from `uname -m`. Packaging and emulation environments can select one explicitly with `OPENBOX_ARCH=x86_64` or `OPENBOX_ARCH=aarch64`.

 #### Manual download

 1. Download the latest release from [GitHub Releases](https://github.com/vindeckyy/OpenBoxGL/releases/latest). Release artifacts are built for both **x86_64** and **aarch64**; pick the one matching your CPU (`uname -m`).
 2. Make it executable. Downloads are not executable by default, and a non-executable AppImage reports "Permission denied" when you try to run it:

 ```bash
 chmod +x OpenBox-$(uname -m).AppImage
 ```

 3. Run it:

 ```bash
 ./OpenBox-$(uname -m).AppImage
 ```

 The first launch starts the Rust server on loopback, writes the per-launch token files into the data directory, and opens the native WebKitGTK window. If WebKitGTK is missing, the launcher prints an install hint and falls back to a chrome-less app window (then your default browser).

 Use `--web` to start the server without a native window:

 ```bash
 ./OpenBox-x86_64.AppImage --web
 ```

 `--web` prints a tokenless loopback URL. Open `http://127.0.0.1:<port>/?token=<value>` with the `server.port` and `server.token` values from the data directory, or send `X-OpenBox-Token` on API calls.

<InstallOptionCard slot="flatpak">

 ### Flatpak

 Install the published bundle, or build from the project's manifest with `flatpak-builder`:

 ```bash
 flatpak install --user --bundle OpenBox-x86_64.flatpak
 flatpak run io.openbox.GameLauncher
 ```

 ```bash
 git clone https://github.com/vindeckyy/OpenBoxGL.git
 cd OpenBoxGL
 cargo build --release --locked -p openbox-cli
 cp target/release/openbox-server .
 flatpak-builder --user --install --force-clean build-dir io.openbox.GameLauncher.yml
 flatpak run io.openbox.GameLauncher
 ```

Download `OpenBox-x86_64.flatpak` from the [release page](https://github.com/vindeckyy/OpenBoxGL/releases/tag/v3.0.0) for the bundle install. The 3.0 Flatpak is 7.1 MiB.

 - The manifest uses the GNOME Flatpak runtime (`org.gnome.Platform` 51) and grants `--filesystem=home`, so Steam, Heroic, Lutris, and ROM folders under your home directory are readable.
 - The Flatpak is not updated by OpenBoxGL's built-in updater. Update by installing a new bundle or rebuilding the manifest with the Flatpak workflow you already use.
 - Flatpak builds install the same `openbox` and `openbox-native` launchers; `flatpak run io.openbox.GameLauncher --web` starts the loopback server without a native window.
</InstallOptionCard>
<InstallOptionCard slot="source">

 ### Source / system

 Source installs build the Rust server. Install Rust 1.92 or newer (the pinned toolchain is 1.99.1), then:

 ```bash
 git clone https://github.com/vindeckyy/OpenBoxGL.git
 cd OpenBoxGL
 cargo build --release --locked -p openbox-cli
 ./openbox.sh
 ```

`./openbox.sh` resolves `target/release/openbox-server` and opens the native window when the host is available. To build the Linux native host:

```bash
make native-host
./openbox-native.sh
```

To start the server without a native window:

```bash
./openbox.sh --web
```

The **Python fallback** still exists for source checkouts. It requires Python 3.11 or newer and is not the shipped backend:

```bash
OPENBOX_BACKEND=python python3 web_app.py
```

For a system install under `/usr/local` (override with `PREFIX=...`):

```bash
make build-rust
sudo make install
openbox          # Native window (default)
openbox --web    # Headless Rust server on loopback
sudo make uninstall  # removes everything the target placed
```

The install target places `openbox-server` under `/usr/local/share/openbox` when it has been built. Build it first with `make build-rust`.
</InstallOptionCard>

<Callout type="caution" title="Known issue: system install wrapper">
The current `sudo make install` wrapper path is not the recommended installation route. Use the AppImage, Flatpak, or source commands above. The wrapper exists for distro-style packaging; the AppImage covers desktop, handheld, and immutable-system use more completely.

## Windows

Windows 10 and 11 on x86_64 and ARM64 are supported through a signed portable install rather than an AppImage. Download the release's `OpenBox-x86_64-windows.zip` (14.6 MiB) or `OpenBox-arm64-windows.zip` (13.8 MiB), extract it, and run the bundled installer at `OpenBox\scripts\install.ps1`; it resolves and pins the release public key, then verifies the archive's SHA-256 checksum and Ed25519 signature before extracting the runtime to `%LOCALAPPDATA%\OpenBox\share\openbox`:

```powershell
$Version = '3.0.0'
Invoke-WebRequest -UseBasicParsing -OutFile OpenBox-x86_64-windows.zip `
  "https://github.com/vindeckyy/OpenBoxGL/releases/download/v$Version/OpenBox-x86_64-windows.zip"
Expand-Archive OpenBox-x86_64-windows.zip -DestinationPath .
Get-Content .\OpenBox\scripts\install.ps1   # read it before running it
powershell -ExecutionPolicy Bypass -File .\OpenBox\scripts\install.ps1 -Tag "v$Version"
```

The release also publishes `install.ps1` as a standalone asset, but it is the same installer that ships inside the archive, and it needs the release verifier (`updates.py`) one directory above it. The verifier is the trust anchor for the Ed25519 check, so it is never downloaded on its own — a fetched verifier could be replaced by whoever served it. Run the standalone copy from the extracted release, where `updates.py` is one directory above it; anywhere else it fails with "The release verifier was not found".

Requirements are Windows PowerShell 5.1, which ships with Windows, and Python 3.11 or newer on `PATH` for the installer's signature verification. The installer verifies signatures with the Python standard library, so neither curl nor OpenSSL is needed; the in-app update check uses the Rust verifier. The portable runtime itself does **not** need Python: `OpenBox\openbox.cmd` launches the bundled `openbox-server.exe`. The installer keeps the previous tree at `share\openbox.previous`, registers the Start Menu shortcut and the `openbox://` protocol handler, and adds the runtime folder to your user `PATH`.

The `openbox.cmd`, `openbox.ps1`, and `openbox-native.ps1` launchers mirror `openbox` and `openbox-native` on Linux: `openbox` opens the native WebView2 window once the host is built and the same UI in a browser app window otherwise, while `openbox --web` always uses the browser. The launchers resolve `openbox-server.exe` first (`OPENBOX_SERVER_BIN`, the install tree, then `PATH`) and fall back to Python only when `OPENBOX_BACKEND=python` is set. Library data lives in `%LOCALAPPDATA%\openbox-game-launcher`.

The release publishes three installers, `install.sh`, `install.ps1`, and `install-macos.sh`, plus `verify_release.py` and `openbox-release.pub`. The uninstaller is not a release asset: it ships **inside** the zip and inside the install tree, so you run it from `scripts\uninstall.ps1` under your install directory (for a default install, `%LOCALAPPDATA%\OpenBox\share\openbox\scripts\uninstall.ps1`) with `powershell -ExecutionPolicy Bypass -File`; add `-InstallDir` for a non-default install, or `-WhatIf` to preview. It removes exactly what the installer created — the install tree and its rollback copy, the user `PATH` entry, the Start Menu shortcut, and the `openbox://` registration — and never touches your library or settings. The [Windows](/windows/) page covers installer options, the native host build, deeplinks, updating, the uninstaller, and Windows troubleshooting in full.

## macOS

macOS 11 or newer on Apple Silicon or Intel installs from the signed universal app bundle (17.4 MiB). Download `install-macos.sh` from the release, read it, and run it with the tag pinned:

```bash
VERSION=3.0.0
curl --proto '=https' --tlsv1.2 --fail --location \
  --output install-macos.sh \
  "https://github.com/vindeckyy/OpenBoxGL/releases/download/v${VERSION}/install-macos.sh"
less install-macos.sh
OPENBOX_RELEASE_TAG="v${VERSION}" bash install-macos.sh
```

The installer verifies the release key, the bundle's SHA-256 checksum, and its Ed25519 signature, then installs `OpenBox.app` into `~/Applications` and links `openbox` into `~/.local/bin`. It needs `python3` 3.11 or newer on your `PATH` to run the release verifier. The bundle itself ships the universal `openbox-server` binary and the WKWebView host with **zero bundled Python**. The bundle is not notarized, so the first launch asks you to allow it in **System Settings > Privacy & Security > Open Anyway**. Re-run with `--replace` to upgrade an existing install. The [macOS](/macos/) page covers the native window, updates, saves, what is hidden on macOS, and troubleshooting.

## Making an app menu entry

Open Settings and choose **Install desktop shortcut** (the button is enabled only when OpenBoxGL detects it is running from an AppImage). This writes a `.desktop` entry under `~/.local/share/applications` pointing at the AppImage's current path. If you move the AppImage afterwards, re-run the install shortcut so the entry follows the new location. Desktop integrators such as Gear Lever also work.

On Windows the portable installer performs the equivalent step for you, writing `OpenBox.lnk` into your Start Menu programs folder and registering the `openbox://` handler. If you move the install, re-register it from the install folder:

```powershell
python -B updates.py install-desktop-entry .\openbox.cmd
```

<Steps>

<li>Run the entry point from a terminal. It should open the native window showing the three-column workspace.</li>
  <li>On first launch with an empty library, the setup dialog (**Set up your library**) appears.</li>
  <li>Settings → About reports the running version, platform, data folder, and whether OpenBox is in its native window or a browser tab. The update status line in Settings shows `· AppImage` when OpenBox runs from an AppImage.</li>
  <li>Your data directory (`~/.local/share/openbox-game-launcher` on Linux, `%LOCALAPPDATA%\openbox-game-launcher` on Windows, or `~/Library/Application Support/openbox-game-launcher` on macOS, unless `OPENBOX_DATA_DIR` is set) now contains `library.json`, `server.token`, and `server.port`.</li>
  <li>`GET /api/v2/version` reports `"version": "3.0.0"`, `"runtime": "rust"`, `"state_schema": 7`, `"plugin_api_version": 2`, `"backup_format": 2`, and `"sync_format": 3`.</li>

</Steps>

## Optional local configuration

OpenBoxGL loads credentials and HTTP-allowlist values from `.env` files it discovers: an explicit `OPENBOX_ENV_FILE` path if set, the data directory and its parent, `~/.env`, and `~/.config/openbox-game-launcher/.env` — plus, on Windows, `%APPDATA%\openbox-game-launcher` and `%LOCALAPPDATA%\openbox-game-launcher`. The current working directory is not searched. A `.env` file is a credential and HTTP-allowlist file only: the provider credentials, the GitHub token aliases, `OPENBOX_ALLOW_HTTP_WEBHOOKS`, and `OPENBOX_ALLOW_HTTP_GAMEYFIN` are read from it, and every other key in the file is dropped silently. The remaining variables — `OPENBOX_SERVER_BIN`, `OPENBOX_BACKEND`, `OPENBOX_ROOT`, `OPENBOX_PORT`, `OPENBOX_MEDIA_ROOTS`, `OPENBOX_SAFE_MODE`, `OPENBOX_SNAPSHOT_DEBOUNCE` (Python fallback only), `OPENBOX_EXECUTABLE`, `OPENBOX_ENABLE_DMABUF`, `OPENBOX_WEBKIT_HARDWARE_ACCELERATION`, `OPENBOX_ENABLE_SQLITE_READ`, and the data-directory and host path overrides — are read from the process environment only, never from `.env`. Each file must be an owner-only regular file (no group or other permission bits; `0o600` is the usual value) and not a symlink. A documented template ships as `.env.example`.

Secrets and tokens (RetroAchievements, EmuMovies, IGDB, GitHub) are read from these files or from the process environment. Put real secrets in `~/.env` or `~/.config/openbox-game-launcher/.env` only, never in the repository or in a tracked file.

<Callout type="caution" title="Two variables that must be set before launch">

- `OPENBOX_DATA_DIR` chooses the data directory. It is read before `.env` bootstrap, so putting it inside a discovered `.env` file is too late.
- `OPENBOX_SAFE_MODE=1` disables plugin execution and the webhook dispatcher for the whole process. Useful for diagnosing plugin-caused launch failures.

</Callout>

See [Configuration](/reference/configuration/) for the full environment contract.

## Where installs keep state

All library data, media, backups, themes, and logs live in `~/.local/share/openbox-game-launcher` on Linux, or in the `OPENBOX_DATA_DIR` you set. They are never inside the AppImage file, and updating or deleting the AppImage does not touch your library.

The Windows portable install uses the same layout under `%LOCALAPPDATA%\openbox-game-launcher`; updating or deleting `%LOCALAPPDATA%\OpenBox` leaves the library untouched. The macOS app stores its data in `~/Library/Application Support/openbox-game-launcher`, and updating or deleting `OpenBox.app` leaves it untouched.

## Troubleshooting

| Problem | Cause / fix |
| --- | --- |
| `Permission denied` on the AppImage | The file is not executable: `chmod +x OpenBox-x86_64.AppImage`. |
| AppImage will not mount | The FUSE 2 library is missing on the host. Install `libfuse2` on Debian/Ubuntu (`libfuse2t64` on Ubuntu 24.04+), `fuse-libs` on Fedora, or `fuse2` on Arch — or run the AppImage with `--appimage-extract-and-run` to skip FUSE entirely. |
| Window does not open | Run from a terminal and read the printed error. In `--web` mode, open the printed `http://127.0.0.1:PORT/` URL yourself — the printed URL carries no token, so take the value from `server.token` in the data directory, send it in the `X-OpenBox-Token` header for API calls, or append it as `?token=<value>` in the browser URL. |
| Source: `openbox-server` not found | Build it with `cargo build --release --locked -p openbox-cli`, or set `OPENBOX_SERVER_BIN` to its path. The launcher falls back to `OPENBOX_BACKEND=python` only when you set it. |
| Source fallback: `python3: command not found` or `ModuleNotFoundError` | The fallback requires Python 3.11+ and must be `python3`. Packaged builds do not need Python. |
| Flatpak can't read Steam/ROMs | Keep folders under your home directory; the manifest grants `--filesystem=home`. |
| Windows: `running scripts is disabled on this system` | Run the script with `powershell -ExecutionPolicy Bypass -File .\OpenBox\scripts\install.ps1`, or set your execution policy for your user. See [Windows](/windows/). |
| Windows: `No Python 3 interpreter found` | Only the installer needs Python. Install Python 3.11+ for `install.ps1`, or launch the portable copy with `OpenBox\openbox.cmd` (no Python required). |
| macOS: app cannot be opened | The bundle is ad-hoc signed and not notarized. Allow it in **System Settings > Privacy & Security > Open Anyway**. |
| Library looks empty after install | Check `OPENBOX_DATA_DIR`, the server reads a different directory than the one you edited. It must be in the process environment at launch. |

More at [Troubleshooting startup and browser](/guides/troubleshooting/startup-and-browser/).

## After installation

Your first launch creates the data directory with an empty library. The window shows the setup dialog (**Set up your library**) when the library is empty; it opens on a six-step quick path (with the longer optional steps behind an **advanced** toggle) that walks you through a guided preview-before-commit scan, emulator readiness checks, metadata match review, and initial preferences. The empty library also offers **Scan a folder**, **Connect a game store**, and **Add one game** directly.
